# Tandem — правила проекта для ИИ-разработчика

Этот файл читается в начале каждой сессии. Соблюдай его всегда. Если задача противоречит этим правилам — остановись и спроси.

## Что за продукт

Tandem — социальная платформа для работы: публичные профили людей и компаний, каталог, и рабочее пространство компании.
Рабочее пространство: Canvas (структура компании), сотрудники, 4 фиксированные роли, рабочие страницы «Задачи» и «Чат», GPS-отметки прихода/ухода.
Полное ТЗ: `docs/TZ_MVP.md` (выгрузка из документа «Tandem — ТЗ MVP (пилот)»). Если в ТЗ чего-то нет — не придумывай, спроси.
Папка `docs/archive/` — старые PDF проектирования. Это история, а не требования: многие правила там отменены. Используй их только как справку и только если об этом попросили; при противоречии всегда прав `docs/TZ_MVP.md`.

Первый пилот: сеть магазинов, 3 филиала, ~100 сотрудников. Основные пользователи работают С ТЕЛЕФОНА.

## Стек

- Next.js (App Router) + TypeScript (strict)
- Supabase: Postgres, Auth, Realtime, Storage
- Vercel (хостинг), GitHub (код), Resend (письма), Sentry (ошибки), PostHog (аналитика)
- Canvas: React Flow (`@xyflow/react`) + автораскладка (`dagre` или `elkjs`)
- Оплата в пилоте — ВРУЧНУЮ (флаг подписки ставит суперадмин). Платёжный провайдер не подключаем.

Не добавляй новые библиотеки и сервисы без явного согласия. Не используй Clerk, Stripe, Redis, векторные БД.

## Архитектура: где живёт логика

Главное правило: права и бизнес-логика живут в базе и на сервере, а не во фронтенде. Позже появятся мобильное и десктопное приложения — они будут ходить в тот же Supabase.

| Слой | Что там |
|---|---|
| Postgres: RLS, constraints, функции (RPC) | кто что видит и меняет; целостность; сложные операции (вступление по ссылке, создание компании, смена роли, смена Scope, GPS-отметка) |
| Supabase Edge Functions / Next.js route handlers | только то, что требует секретов или внешних сервисов (email, будущие вебхуки оплаты) |
| Next.js UI | показать данные, вызвать RPC, показать ошибку. Никаких проверок прав, на которые опирается безопасность |

## База данных

База УЖЕ создана в Supabase (проект Tandem, Франкфурт) и покрыта тестами прав. Описание функций и кодов ошибок — `supabase/README.md`, правила работы с ней — скилл `tandem-supabase`.

- **Не создавай и не меняй миграции**, не выполняй SQL в базе. Если экрану не хватает таблицы или функции — остановись и опиши, чего не хватает.
- Чтение — `select` (RLS отдаёт только разрешённое). Изменения — через RPC. Исключения: Owner/Admin меняют `units` и `unit_members` напрямую; Owner/Admin меняют свою строку `organizations` напрямую — только `name`, `city`, `description`, `logo_url` (`slug` после создания не меняется, чтобы не ломать ссылки); пользователь — свою строку `profiles`.
- Пилот: один пользователь — одна компания. Не завязывай код на это правило: позже его снимем.
- Отправка сообщений идемпотентна: `client_id` генерируется на клиенте один раз на сообщение.
- GPS-отметку и расстояние считает сервер (`check_attendance`). Клиент только передаёт координаты и точность.

## Безопасность

- Ключ `service_role` никогда не попадает в клиентский код и в переменные `NEXT_PUBLIC_*`.
- Скрытая кнопка — не защита. Каждая операция проверяется в RLS/RPC.
- Realtime-подписки только на доступные пользователю страницы. После потери доступа события не приходят.
- Для каждой новой таблицы или политики пиши тест: пользователь компании A не может прочитать/изменить данные компании B; сотрудник без доступа к странице получает отказ.

## Скиллы и агенты проекта (`.claude/`)

- `tandem-supabase` — как экраны работают с нашей базой (RPC, ошибки, Realtime, картинки, GPS). Используй при любой работе с данными.
- `nextjs-turbopack`, `security-review`, `postgres-patterns`, `database-migrations` — из открытого набора ECC (MIT, см. `.claude/ECC-LICENSE`).
- Агент `database-reviewer` — для проверки SQL, если база понадобится менять.

## Модули

Два вида модулей:
- модули страниц (`tasks`, `chat`, будущие): много экземпляров, доступ через Scope и `page_access`;
- модули компании (`attendance`, будущие графики смен): один на компанию, привязан к подразделениям.

Каждый модуль: своя папка `src/modules/<имя>/`, свои таблицы с `organization_id`, права через общие функции доступа, запись в реестре `modules` и флаг в `organization_modules`. Новый модуль не должен менять код существующих.

## Структура папок

```
src/
  app/            # маршруты Next.js (тонкие страницы)
  components/     # общие UI-компоненты
  modules/
    tasks/
    chat/
    attendance/
    canvas/
  lib/
    supabase/     # клиенты Supabase (browser / server)
    i18n/         # все строки интерфейса (сейчас ru; позже kk, en)
supabase/
  migrations/
  tests/          # тесты RLS и RPC
docs/
  TZ_MVP.md
  tasks.md        # текущий план задач
```

## Интерфейс

- Mobile-first: каждый экран сначала проверяется на ширине 375px.
- Светлая тема, русский язык. Тексты интерфейса — только через `lib/i18n`, не хардкодить в компонентах.
- Пустые состояния и ошибки — понятным языком, без технических терминов.

## Как работаем

1. Сначала план: какие файлы меняешь и зачем. Код — только после подтверждения.
2. Одна задача — один небольшой коммит с понятным сообщением.
3. Задачи берём из `docs/tasks.md`; после выполнения отмечай их там.
4. Каждую миграцию и RLS-политику объясни простыми словами в ответе.
5. Перед коммитом: `npm run lint`, `npm run typecheck`, тесты RLS.
6. Если не уверен в продуктовом правиле — спроси, не додумывай.
7. Пользователь не пишет код и не вводит команды вручную. Все команды (git, npm, supabase и любые другие) выполняет ИИ сам: сначала показывает, что собирается сделать, и спрашивает подтверждение. Если нужна авторизация в сервисе — объясни, что именно нажать.

## Чего НЕ делать в MVP

Лента, личные сообщения, файлы и вложения, звонки, PWA и нативные приложения, тёмная тема, кастомные роли, персональные разрешения, точечные запреты, подзадачи, автоархив по таймеру, онлайн-оплата, тарифы Business/Company.
